## 0. Qué es y qué no

Es el backend local de Sandbox sin bridge:
- el documento de escena con su esquema v1 y su validador (A1);
- el almacén: tandas atómicas con autor, revisiones, huellas, conflictos, horizonte, deshacer condicionado por campo, deduplicación y guardado atómico (A5, I2, I3);
- la API HTTP y el flujo SSE con reconexión sin huecos (I1, I5), con credenciales distintas para la persona y la IA y Host/Origin (E1);
- aplicar por revisión aprobada, que en F1a solo deja la orden en la cola con su estado (I4, D2), porque no hay bridge.

No es:
- el bridge, los peers ni el mod falso (F1b, que depende de S-puente);
- la vista mínima de la web ni su sesión de navegador con cookie y CSRF (F1b);
- el préstamo de uso, la fachada MCP ni los casos CO-1 a CO-10 completos (F1-co);
- la máquina de toma (F5): aquí la toma es un estado que las pruebas fijan desde dentro (§5.4).

Trazabilidad (R20): §2 sale de #7 y del prototipo (`ui/prototipo/estudio.html`, `DOC14`); §3 y §4, del plan de co-edición §2.1, §2.2, §2.4 y §2.7; §5, de #1, #23, E1 y del plan de co-edición §2.5. Lo que no trace a esto no entra.

### 2.1 Reglas de forma
- `kind` ∈ {`actor`, `objeto`, `infectado`, `animal`}; prefijo de id por tipo: `act`, `obj`, `zmb`, `ani`; cámaras `cam`. Ids `<prefijo>-<n>` con `n` ≥ 1 en decimal con al menos dos cifras.
- Solo actores llevan `wardrobe`, `behaviour` (∈ HOLD, ONCE, LOOP, ROAM), `roam`, `marks` y `gestures`. Un gesto lleva `emote` y exactamente uno de `at` (índice de marca, entero ≥ 1) o `t` (segundos ≥ 0).
- Coordenadas en metros con un decimal; `yaw` en grados [0, 360). `ambiente`: `nubes`, `niebla`, `lluvia` en [0, 1]; `viento` en [0, 20] m/s; `hora` `HH:MM`.
- Claves de cámara con `t` estrictamente creciente y la primera en 0.
- **Ids sin reutilizar** (co-edición SOL-C03): `next` guarda el siguiente número por prefijo y solo crece; un id nuevo siempre es `<prefijo>-<next>` y luego `next` sube, aunque se hayan borrado entidades.

### 2.2 Hash
SHA-256 en hex de `json.dumps(doc, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")`. La revisión no va dentro del documento, así que no entra en el hash.

### 2.3 Validador (`app/backend/validate.py`)
`validate(doc: dict, catalog: dict) -> list[dict]`, cada error `{"code", "pointer", "msg"}` con `pointer` en JSON Pointer (RFC 6901). Lista vacía = válido. Códigos (A1): `unsupported_version` (`schema` distinto), `unknown_field`, `missing_field`, `bad_type`, `bad_value`, `unknown_class` (clase que no está en el catálogo para su `kind`), `out_of_map` (x o z fuera de [0, 15360]), `budget_exceeded` (por tipo, más que el tope del catálogo; pointer `/entities`), `bad_ref` (gesto con `at` mayor que el número de marcas), `bad_order` (claves de cámara), `bad_id` (id que no sigue §2.1 o repetido).

Catálogo de prueba `fixtures/catalog-m1.json`: `{"classes": {"objeto": [...], "infectado": [...], "animal": [...], "actor": [...]}, "caps": {"objeto": 20, "infectado": 10, "animal": 3, "actor": 2}, "wardrobes": [...], "emotes": [...]}` con las clases, vestuarios y gestos del prototipo. El catálogo real llega del mod en F1b.

## 3. El almacén (`app/backend/store.py`)

### 3.1 Operaciones y sus huellas

| `name` | `target` | `args` | huella (entidad, campo) |
|---|---|---|---|
| `entity.add` | — | `kind`, `cls`, `name`, `x`, `z`, `yaw` y los de actor | (id nuevo, `*`) |
| `entity.delete` | id | — | (id, `*`) |
| `entity.move` | id | `x`, `z` | (id, `x`), (id, `z`) |
| `entity.set` | id | cualquiera de `cls`, `name`, `yaw`, `wardrobe`, `behaviour`, `roam` | (id, cada campo dado) |
| `entity.marks` | id de actor | `marks` (lista entera) | (id, `marks`), (id, `gestures`) |
| `entity.gestures` | id de actor | `gestures` (lista entera) | (id, `gestures`) |
| `ambient.set` | — | cualquiera de los campos de `ambiente` | (`ambiente`, cada campo dado) |
| `camera.add` | — | `name`, `keys` | (id nuevo, `*`) |
| `camera.delete` | id | — | (id, `*`) |
| `camera.set` | id | `name` y/o `keys` | (id, cada campo dado) |

- `(id, *)` se cruza con cualquier campo de ese id. `entity.marks` incluye `gestures` porque los gestos con `at` dependen de las marcas.
- Dentro de una tanda, `target` puede ser `"$n"`: el id creado por la operación `n` (0-based) de la misma tanda.
- Cualquier otro `name`, o args que sobren, → `bad_op` con su pointer (`/ops/<i>/name` o `/ops/<i>/args/<clave>`).

### 3.2 API de la clase

```python
class Store:
    def __init__(self, path: str, catalog: dict, horizon: int = 1000): ...
    lock: threading.RLock          # público: el servidor publica eventos dentro de él (§5.3)
    on_commit: callable | None     # lo llama commit() dentro del candado con el registro de §3.6
    gate: callable | None          # gate(author) -> code | None, dentro del candado (pausa, toma)
    def snapshot(self) -> dict     # {"doc_id", "rev", "hash", "doc"} (copia profunda)
    def commit(self, author: dict, request_id: str, doc_id: str, base_rev: int, label: str | None, ops: list) -> dict
    def undo(self, author: dict, request_id: str, doc_id: str) -> dict
    def redo(self, author: dict, request_id: str, doc_id: str) -> dict
    def revert_batch(self, author: dict, request_id: str, doc_id: str, batch_id: str) -> dict
    def freeze(self, doc_id: str, rev: int, hash: str) -> dict   # §3.8
```

`author` = `{"role": "human" | "ai", "id": str}`; lo pone el servidor a partir de la credencial (§5.2), nunca el cuerpo.

Resultado: `{"ok": true, "rev", "hash", "batch", "created": [ids], "partial": [{"target", "field", "why"}]}` o `{"ok": false, "code", "pointer", "msg", "current": {...}}`. Nunca lanza por una entrada del cliente.

### 3.3 Orden dentro del candado (co-edición SOL-C11)

Todo `commit`, `undo`, `redo`, `revert_batch` y `freeze` corre entero dentro de `lock`, en este orden, y para en el primer rechazo sin tocar nada:
1. deduplicación (§3.7);
2. `doc_id` igual al abierto → si no, `doc_changed`;
3. `gate(author)` → su código (`ai_paused`, `take_locked`);
4. `base_rev` ≤ `rev` → si no, `bad_base`; `rev − base_rev` ≤ `horizon` → si no, `stale_base` con `current` = instantánea;
5. forma de cada operación → `bad_op`; target que no existe → `entity_gone`;
6. conflictos (§3.4);
7. aplicar todas las operaciones sobre una **copia** y validar la copia (§2.3) → si hay errores, `invalid` con el primero y `errors` con todos;
8. publicar: el documento nuevo, `rev + 1`, el registro de la tanda y el guardado atómico (§3.9); llamar a `on_commit`.

Una tanda es todo o nada: si falla cualquier paso, el documento, `rev`, el historial y el fichero no cambian (SOL-C04).

### 3.4 Conflictos (co-edición §2.2, SOL-C02)

La huella de la tanda es la unión de las de sus operaciones. Se cruza con la de cada tanda confirmada con revisión > `base_rev`.
- **IA**: cualquier cruce → `conflict`, con `current` = los valores actuales de lo cruzado y `pointer` a la primera operación que cruza.
- **Persona**: los cruces no rechazan; su tanda se aplica sobre el estado actual (última escritura gana). Solo la rechazan `entity_gone` y los pasos 1-5 y 7.

### 3.5 Inversas y deshacer (co-edición §2.4, SOL-C06, SOL-C07)

- Cada tanda guarda, por operación, el valor **antes** (del estado real justo antes de su commit) y **después** de cada campo de su huella; para `add` y `delete`, la entidad entera.
- `undo(author)`: la última tanda propia sin deshacer de ese autor, y `redo(author)` la última deshecha. Se ejecuta como una tanda nueva del mismo autor (`label` «Deshacer: …» o «Rehacer: …») que, por cada campo: si su valor actual es el «después», pone el «antes»; si no, lo deja y lo apunta en `partial` con `why: "changed_later"`. Deshacer un `add` borra la entidad solo si todos sus campos siguen como los creó; si no, `partial`. Deshacer un `delete` la recrea con su id original (que no se reutiliza, §2.1). Una tanda nueva del autor vacía su pila de rehacer.
- `revert_batch(author, batch_id)`: lo mismo para una tanda concreta, de cualquier autor; solo la persona puede llamarlo (si no, `forbidden`). Una tanda ya revertida → `already_reverted`.
- Sin ninguna tanda que deshacer o rehacer → `nothing_to_undo` / `nothing_to_redo`.

### 3.6 Registro de una tanda

`{"batch": "b-<rev>", "rev", "hash", "author", "label", "ops", "created", "partial", "fp": [[target, field], ...], "at_ms"}`. Se guardan los últimos `horizon` registros en memoria (deque); son los que mira §3.4 y los que repite el SSE.

### 3.7 Deduplicación (SOL-C05)

Por `request_id`, con los últimos `horizon` en memoria: mismo id y mismo contenido canónico (autor, doc_id, base_rev, label, ops) → el mismo resultado guardado, sin volver a aplicar; mismo id y otro contenido → `request_conflict`.

### 3.8 Aplicar lo aprobado (co-edición §2.7, SOL-C12)

`freeze(doc_id, rev, hash)` dentro del candado: si `rev` y `hash` son los actuales, devuelve `{"ok": true, "rev", "hash", "doc"}` con una copia profunda congelada; si no, `stale_apply` con lo que cambió desde `rev` (los registros de §3.6). Solo la persona (lo comprueba el servidor).

### 3.9 Fichero

`path` guarda `{"rev": n, "doc": {...}}`. Escritura atómica: fichero temporal en el mismo directorio, `flush` + `os.fsync` y `os.replace`. Si el fichero no existe, se crea con `fixtures/escena-basica-cine.json` en `rev` 1. Al abrir uno ilegible o inválido: no se sobrescribe, error claro y salida 2 del servidor. El historial y las pilas de deshacer no se guardan (al reiniciar empiezan vacías).

## 4. Qué no hace el almacén

No conoce HTTP, SSE, credenciales ni la toma: eso entra por `author`, `gate` y `on_commit`.

## 5. El servidor (`app/backend/server.py`)

`python app/backend/server.py --config backend.json [--port N]`. `backend.json`: `{"port": 8765, "scene": "data/scene.json", "catalog": "fixtures/catalog-m1.json", "human_key": "...", "ai_key": "..."}`; si faltan las claves, las genera con `secrets.token_urlsafe(32)`, las escribe en el fichero y no las imprime.

### 5.1 Endpoints

| Método y ruta | Quién | Cuerpo | Respuesta |
|---|---|---|---|
| `GET /api/scene` | los dos | — | `snapshot()` |
| `POST /api/scene/ops` | los dos | `{doc_id, request_id, base_rev, label, ops}` | resultado de `commit` |
| `POST /api/scene/undo` · `/redo` | los dos | `{doc_id, request_id}` | resultado |
| `POST /api/scene/batches/<id>/revert` | persona | `{doc_id, request_id}` | resultado |
| `POST /api/ai/pause` | persona | `{paused: bool}` | `{paused}` |
| `POST /api/apply` | persona | `{doc_id, rev, hash}` | `{ok, op_id}` o `stale_apply` |
| `GET /api/events` | los dos | — | SSE (§5.3) |

- HTTP: 200 con `ok: true`; 409 para `conflict`, `stale_base`, `stale_apply`, `doc_changed`, `request_conflict`, `take_locked`, `ai_paused`, `already_reverted`, `nothing_to_*`, `entity_gone`; 422 para `bad_op`, `invalid`, `bad_base`; 401 sin credencial válida; 403 `forbidden` o `author_mismatch`; 400 para JSON ilegible o más de 1 MiB.
- Un cuerpo que traiga `author` → 403 `author_mismatch` si no casa con la credencial, y se ignora si casa (SOL-C01).
- `POST /api/apply`: con `freeze` correcto, crea una orden en la cola con estado `pendiente`, el `rev` y el `hash` congelados como revisión pedida, y emite su evento `op.state`. En F1a nada la despacha (no hay bridge).

### 5.2 Credenciales, Host y Origin (E1)

- `Authorization: Bearer <clave>`; `human_key` → `{"role": "human", "id": "web"}`, `ai_key` → `{"role": "ai", "id": "mcp"}`. Comparación con `hmac.compare_digest`. Sin cabecera o con otra clave → 401, sin decir cuál falló.
- `Host` tiene que ser `127.0.0.1:<port>` o `localhost:<port>`; si trae `Origin`, `http://127.0.0.1:<port>` o `http://localhost:<port>`. Si no → 403 sin efectos. Sin cabeceras CORS.
- `gate`: la IA con `paused` → `ai_paused`; cualquier autor con `take_state` ∈ {`armada`, `rodando`} → `take_locked`. `paused` y `take_state` son atributos del servidor; `/api/ai/pause` los cambia **dentro del candado** del almacén. La IA nunca llega a `apply`, `revert` ni `pause` (403).

### 5.3 SSE y reconexión (co-edición §2.5, SOL-C09, SOL-C13)

- `seq` global del flujo, distinto de `rev`. Cada evento lleva `id: <seq>`, `event: <tipo>` y `data:` en una línea JSON:
  - `scene.commit`: el registro de §3.6;
  - `op.state`: `{op_id, state, rev, hash, at_ms}` (estados de #23);
  - `ai.state`: `{paused}`;
  - `snapshot`: `{rev, hash, doc_id, doc, ops}` con `ops` = estado actual de cada orden de la cola.
- Los eventos se crean **dentro del candado** del almacén (desde `on_commit` y desde los cambios de cola y pausa), con su `seq`, y se guardan en un anillo de `horizon` eventos.
- Al conectar, dentro del candado: si `Last-Event-ID` está en el anillo, se encolan para ese cliente los eventos posteriores; si falta o es más viejo que el anillo, un `snapshot` con el `seq` actual. Luego el cliente queda suscrito, aún dentro del candado, así que ningún evento cae entre la instantánea y la suscripción.
- Cada cliente tiene su cola acotada (1000); si se llena, se le cierra la conexión y al volver recibe `snapshot`. Un comentario `: ping` cada 15 s.

### 5.4 Para las pruebas

Las pruebas arrancan el servidor en un hilo con puerto 0 y fijan `server.take_state` desde dentro. Nada de endpoints de depuración.

## 9. Fuera de alcance y riesgos
