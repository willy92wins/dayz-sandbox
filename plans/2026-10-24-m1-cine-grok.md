# Plan M1 cine — DayZ Sandbox (lane Grok)

2026-10-24 · lane ciega · contrato: `product-spec.md` criterios A–E · versiones: dayz-mcp `b8c8d105`, DayZ-Script-Diff `e8204c69`, Expansion AI 1.9.80 commit `0d26645`

Este plan construye el hito M1 (estudio local de escenas para cine/machinima en Chernarus). F–H (standalone, mapas, fachada MCP) quedan fuera. Nada se implementa aquí.

Convenciones: `[I]` = inferencia; `[verify]` = lo cierra un spike; afirmaciones de código con `ruta:línea`. La verdad de un gate es el estado leído en el juego, no un HTTP 200.

## 1. Decisiones de arquitectura

### D-ARCH-1 — Tres piezas originales: backend + web + mod propio

**Elegido:** un servicio HTTP local (Python 3.12) que posee el documento de escena, la cola y la autenticación; una web TypeScript/React/Vite; un mod Enforce nuevo (addon servidor + addon cliente) que hace long-poll al servicio. El MCP de dayz-mcp **no** es el runtime de M1.

**Descartado:** reutilizar dayz-mcp como el bridge de producción (el spec exige E3: A–D con el MCP apagado). dayz-mcp queda como arnés de spikes y paridad (consolidado §9).

**Por qué:** `MCPBridge.c:157-227` ya demuestra RestApi + RestContext + `SetHeader("application/json")` y URL de loopback; `loopback.py:219` fija bind `127.0.0.1`. Copiar el **patrón** (pull, credencial, TTL, allowlist) a un mod nuevo evita mezclar el lease de Cowork con el producto. Python reutiliza la disciplina de esquema de `loopback.py` (validar en la entrada, nunca en el tick). TypeScript en el backend unificaría con la web pero duplicaría el banco de pruebas de dayz-mcp que ya está medido (`README.md:104`, `/poll` 600 ms, 4741 ticks).

**Traza:** E1, E3; consolidado §9.

### D-ARCH-2 — El juego llama; el servicio responde (pull)

**Elegido:** el mod hace GET asíncrono a `http://127.0.0.1:<puerto>/v1/poll?key=...` y POST de resultados. Nunca `*_now` en el tick del juego.

**Descartado:** el backend empuja RPC al juego (no hay servidor TCP en Enforce para eso) o REST sincrónico en `OnUpdate`.

**Por qué:** `MCPBridge.c:153` (`StartPoll`) y consolidado §5. Las acciones de cine (camino de cámara, spawn por lotes) se **programan** dentro del juego con deadline/TTL; HTTP no dirige cada frame.

**Traza:** E2; consolidado §5 transporte.

### D-ARCH-3 — Documento de escena = JSON Schema versionado en el backend; ids lógicos, no `object_id`

**Elegido:** `scene.schema.json` (draft 2020-12) con `schemaVersion` entero, ids lógicos de entidad, vocabulario de comportamiento `HOLD | ONCE | LOOP | ROAM`, presets de vestuario por nombre, cámaras y tomas. El backend valida **antes** de encolar. El mod mantiene un registro de propiedad `scene_id → {logical_id → runtime_id}` solo en RAM de sesión.

**Descartado:** guardar `object_id` del bridge (no sobreviven al reinicio; consolidado §5, tickets ficha 5); export Object Spawner como formato canónico (no cubre actores, cámaras ni gestos).

**Por qué:** A1–A4, C4. El reset (A3) solo borra runtime_ids del registro; nunca toca `$profile:storage`.

**Traza:** A1–A4, C4.

### D-ARCH-4 — Expansion AI como addon opcional, llamadas a API pública en runtime, cero derivación

**Elegido:** addon `DayZSandbox_ExpansionAdapter` que solo se carga si el usuario tiene Expansion Core + AI. El núcleo `DayZSandbox` no referencia tipos `eAI*`. Detección: `#ifdef EXPANSIONMODAI` en el **adapter** (`DayZExpansion_AI_Defines.c:3-6`) **y** un probe en runtime (`GetGame().ConfigIsExisting("CfgVehicles eAI_SurvivorM_Boris")` [I] — el probe concreto lo cierra S3-ingame). Fail-closed: escena con actores → `expansion_unavailable` y **cero** spawns (C5).

Mapeo C4 (propio → Expansion, leído en S3 offline):

| Vocabulario escena | Expansion `eAIWaypointBehavior` (`AIenums.c:1-13`) |
|---|---|
| HOLD | `HALT` |
| ONCE | `ONCE` |
| LOOP | `LOOP` |
| ROAM | `ROAMING` |

Spawn: `CreateObject` / `CreateObjectEx` vanilla (`game.c:703`) + `ai.SetGroup` / `eAIGroup.CreateGroup` / `AddWaypoint` / `SetWaypointBehaviour` / `ExpansionHumanLoadout.Apply` llamados por nombre desde el adapter. **No** se copia `eaicommandmanager.c:376-390`.

**Descartado:** `modded class eAIBase` en el núcleo (deriva y enreda M2); bot_start de dayz-mcp (TTL ≤ 30 s, solo diag; consolidado §5).

**Traza:** C1–C5; spike S3; licencia CC BY-NC-ND.

### D-ARCH-5 — Cámara scripted en el cliente; nunca FreeDebugCamera para tomas

**Elegido:** el addon cliente crea `Camera` (no `FreeDebugCamera`), `SetActive(true)`, pose con `SetPosition`/`SetOrientation`/`SetFOV`/`SetFocus`. Caminos: evaluación **por frame** en `OnUpdate` del cliente (Catmull-Rom en posición, slerp de orientación, lerp de FOV y focus), con reloj de toma `t` en segundos de simulación. Parar: desactiva la cámara y restaura gameplay.

**Descartado:** encadenar `Camera.InterpolateTo` como camino canónico (solo interpola entre **instancias** de Camera, `camera.c:24`; no lleva FOV/focus por clave; el probe S-CAM decide si se usa como aceleración de tramos rectos). FreeDebugCamera (`MCPClientBridge.c:5726+`) congela simulación (consolidado §5).

**Por qué:** B1–B4; dayz-mcp ya aplica cámara scripted (`MCPClientBridge.c:5704-5721`).

**Traza:** B1–B4.

### D-ARCH-6 — Toma = transacción observada, no un script de timeline en la web

**Elegido:** el documento declara `takes[]` con `cameraPathId`, `actorCues[]` (marca + gesto), `weather`, `timeOfDay`. `POST /v1/takes/{id}/start` valida, aplica clima/hora, arranca camino y cues en el **mismo lote** entregado al poll. Estados: `pending → executing → observed | failed | partial`. `POST /v1/takes/{id}/stop` aborta camino y HOLD a actores; control al director en < 1 s (B5).

**Descartado:** la web dispara N tools MCP en serie (latencia por poll; tickets ficha 1).

**Traza:** B5–B7, D2.

### D-ARCH-7 — Web: mapa 2D estático + Dockview MIT + estados observados

**Elegido:** React 18 + Vite + OpenLayers con **una imagen propia** de Chernarus (licencia documentada; D5). Dockview (MIT) para paneles. SSE desde el backend para la cola. Atajos con tinykeys, reasignables en JSON de usuario. Sin viewport 3D.

**Descartado:** teselas iZurvive/xam.nu (D5); Theatre Studio (AGPL); controlar el juego vía MCP desde el navegador.

**Traza:** D1–D5, E3.

### D-ARCH-8 — Banco de pruebas: dayz-mcp primero, Sandbox después

**Elegido:** las capacidades P0 de las fichas 1–13 se **miden** en dayz-mcp (mismo PC, lease, Chernarus) cuando el verbo ya existe o se prototipa ahí; el mod Sandbox reimplementa el patrón con su wire propio. Fichas 14–15 (nav/survivor) son M2; ficha 16 es eventos/RP. No se copian ficheros de dayz-mcp al PBO de Sandbox; se reescriben.

**Descartado:** implementar primero en Sandbox sin números de paridad.

**Traza:** referencia de paridad del spec; tickets.

### D-ARCH-9 — Presupuestos duros salen de E5, no de la wiki de Expansion

**Elegido:** topes iniciales **provisionales** (documentados como hipótesis, no como criterio): ≤ 20 objetos de atrezo, ≤ 10 infectados, ≤ 3 animales, ≤ 4 NPC Expansion, 1 cámara activa. E5 mide FPS de servidor (media y mínimo en 60 s) con esa carga y con 2× carga; A6 usa los topes **fijados tras E5**. Hasta entonces A6 rechaza por el tope provisional y el test de A6 se marca incompleto si E5 no ha cerrado.

**Descartado:** copiar «> 30 IA degradan» de Expansion como número de producto.

**Traza:** A6, E5.

## 3. Fase 0 — Spikes (antes de construir producto)

Cada spike termina en **PASA / FALLA / INCONCLUSO**. FALLA bloquea la fase que lo nombra. INCONCLUSO no se cuenta como PASA.

### S-BIND — loopback y credencial (offline + humo)

- **Qué:** el prototipo de F1 solo escucha `127.0.0.1`; `?key=` inválida → 401 y el log del dispatcher no registra comando.
- **Cómo:** `python -m http.server` no. Servidor mínimo que copie el 401 de `loopback.py:5670`. Desde otra interfaz de la máquina: `curl http://<LAN-IP>:port/v1/health` debe fallar (connection refused). `curl "http://127.0.0.1:port/v1/poll?key=wrong"` → cuerpo `{"error":"unauthorized"}`, exit 0 de curl con HTTP 401.
- **PASA:** bind comprobado con `Get-NetTCPConnection -LocalAddress 127.0.0.1`; 401 en clave mala; 0 líneas `cmd=` en el log.
- **FALLA:** escucha en `0.0.0.0` o 200 con clave mala.
- **Criterio futuro:** E1.

### S-POLL — p95 poll Diag (in-game)

- **Qué:** N=100 round-trips `poll vacío → result noop` con marcas de tiempo en servicio y en el log del mod.
- **PASA:** p95 < 1,0 s; ningún tick síncrono HTTP (grep del addon: cero `GET`/`POST` fuera de callbacks RestApi).
- **FALLA:** p95 ≥ 1 s o freeze de simulación.
- **INCONCLUSO:** solo Diag, retail pendiente (lo cierra F6).
- **Criterio:** E2.
- **Base:** `README.md:104` 600 ms / 4741 ticks en dayz-mcp.

## 5. Cláusula de desafío del spec

### (a) Criterios que chocan con su Intent

- **B3 vs Intent «planos limpios»:** si el DOF de BI depende de un ajuste de vídeo del usuario, el criterio binario puede FALLAR con el Intent cumplido (desenfoque de director imposible en esa máquina). Surfacear tras S-DOF.
- **B2 «misma prueba contra COT»:** COT es referente, no dependencia. Medir contra COT cuando esté; empaquetarlo viola F1 futuro y la regla de no derivar. El Intent de B2 es suavidad y puntualidad, no paridad byte a byte con COT.
- **C5 «escena con actores se rechaza entera»:** el Intent es no dejar medio-mundo sin NPC. Rechazar **también** el atrezo de esa apply es duro pero coherente. Alternativa más simple: aplicar objetos e infectados y marcar actores `failed` — **choca con C5 literal**. Se pregunta en Grill (Q3).
- **A5 undo 20 ops:** el Intent de A es «aplicar/resetear idéntica». Undo de documento no deshace el mundo. Si la UI no distingue, choca con §6 del consolidado. El plan mantiene undo **solo documento** y reset **solo sesión**.

### (b) Caminos más simples que cumplen el Intent

- **B2:** Catmull-Rom per-frame cubre travelling/paneo; InterpolateTo solo si S-CAM lo demuestra más estable. No hace falta shake ni easing tipo COT en M1 (el spec no pide shake).
- **D3:** `localStorage` de un layout JSON propio, sin Dockview, cumple «paneles movibles y restaurados» con CSS grid + drag. Dockview es conveniente, no necesario. Recomendación: Dockview MIT si el bundle se audita; si no, grid propio.
- **C1:** vestuario por `CreateObjectEx` + attach vanilla, sin `ExpansionHumanLoadout.Apply`, reduce superficie legal. Usar Apply **solo** si S3.1 FALLA con la vía vanilla.

### (c) Criterios que faltan (Intent sin gate)

- **Catálogo de clases certificado por versión 1.30** (A1 «clase desconocida» necesita lista). Falta criterio «el catálogo se genera de `CfgVehicles` del modset y se versiona».
- **Unidad de FOV** (radianes vs grados) no está en B1.
- **Reloj de toma:** B2 usa segundos de simulación; si el servidor va a 0,5× no está dicho. Falta «t es tiempo de mundo, no de pared».
- **Cliente único director:** no hay criterio de «rechazar segundo cliente Steam». Intent C lo asume. Recomendación: fail-open (el segundo cliente no rompe) y no gastar M1 en lock.
- **OBS:** fuera de producto; falta un criterio negativo «ningún endpoint graba frames» para no resbalar a MakeScreenshot (roto, consolidado §5).

## Cómo se pone cada gate en ROJO (resumen de medida)

Un gate está en ROJO cuando la **lectura en juego o el rechazo pre-juego** no cumple la columna Esperado. HTTP 200 no lo pone en VERDE.

| Gate | Cómo se pone ROJO |

| A1 | fixture inválida produce 0 errores de path **o** el log del bridge muestra `scene_apply` |

| A3 | queda un id propio vivo **o** desaparece el objeto a mano **o** cambia mtime de storage |
| A4 | hash cambia sin edits **o** recarga desplaza ≥ 0,5 m |
| A5 | hash post-undo ≠ inicial |
| A6 | over-budget llega a poll |

| B6 | una de 3 tomas desvía marca/path/conteo |
